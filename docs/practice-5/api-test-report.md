# API-тесты СМП — отчёт

Проверяем HTTP-контракты СМП: авторизацию, операции с картами, логирование,
поиск транзакций, Dashboard и симуляторы. Для каждого сценария проверяем
HTTP-код, тело ответа и изменения состояния, доступные через API.
Суммы и лимиты задаём в копейках.

Тесты размещены в модуле [`services/api-tests`](../../services/api-tests).
Запускаем их профилем `api-tests` на отдельном
[`Compose-стенде`](../../docker-compose.api-tests.yaml).
Автоматический запуск настроен в [CI](../../.github/workflows/api-tests.yml).

Основной набор проверяет реализованные HTTP-контракты. Для известных
расхождений и рисков выделен `KnownContractDefectsTest` с тегом `known-defect`.
Эти 12 проверок сохраняют ожидаемое поведение и на текущей реализации падают;
запускаем их отдельно от регрессии.

`status/error/path/timestamp`, но не объясняют, какое поле отклонено — D-06.

типы, enum, форматы RRN/authCode и неотрицательное время. `nullValue()` проверяет
значение nullable-полей; `required` в схеме проверяет наличие поля.
Значение MTI проверяем отдельно в D-01.

Все D-01..D-12 воспроизведены отдельным запуском `KnownContractDefectsTest`:
12 падений на проверках ожидаемого результата, 0 ошибок выполнения.

| ID | Декларировано / проверяемый риск | Наблюдается | Источник и классификация |
|---|---|---|---|

Дополнительные несовпадения источников:

- `api-spec.md` перечисляет меньше методов карт, чем контроллеры и OpenAPI.
  PATCH/DELETE/список/reserve/rollback и bulk-update взяты из кода и YAML.
- `issuerId` и `mcc` поиска отсутствуют в кратком Markdown-контракте, но есть
  в OpenAPI и реализации. Они покрыты, фильтр `stan` не используется.
- OpenAPI обещает `/terminal/start` и `/terminal/status`. Их нет в контроллере;
  существуют `/start-continuous` и `/stop`. Отсутствующие ресурсы терминала
  ошибочно обрабатываются как 500. Требования start/status не считаются выполненными.
- `/api/simulator/merchants` существует напрямую, но не доступен через Gateway.
- `/api/internal/log`, authorize, rollback и route не имеют внешних маршрутов
  Gateway. Для внутренних контрактов используются прямые сервисные адреса.
- `/api/bins`, `/api/bin`, `/api/notifications` также не проксируются Gateway.
- Ошибки Bin Lookup 404/500 имеют пустое тело. Это ограничение контроллера,
  отдельные проверки фиксируют пустоту, а не ожидают несуществующий ErrorResponse.
- Для `POST /api/cards` краткий api-spec обещает 409 на существующий PAN,
  но PAN генерирует сервер и входной DTO не позволяет задать его. Такой конфликт
  не имеет воспроизводимого клиентского класса входов; внутренние коллизии
  генератора проверяются на другом уровне.
- Для внутреннего route OpenAPI указывает 503; оркестратор при недоступной
  Authorization возвращает доменный отказ в HTTP 200. Публикация в брокер тоже
  завершается 200/96 при успешной компенсации. Внешний 503 возникает, когда
  Gateway не может соединиться с самим Switch.
- `GET /api/cards` имеет максимум 10000, превышение даёт 413, а не общий 400.
  Его default 10 согласуется с OpenAPI и контроллером; service default 50
  перекрывается defaultValue контроллера.

При расхождении источников фиксируем фактический HTTP-ответ и сохраняем
проверку ожидаемого поведения из контракта в отдельном тесте.

## 5. Обоснование достаточности

Выделяем классы входных данных: допустимые значения, отсутствие/null/blank,
неверная длина и недопустимые символы. Для ограниченных значений проверяем
границу и соседние значения. В негативном тесте нарушаем одно правило.
Для каждого денежного сценария создаём отдельную карту с заданными балансом,
лимитами и статусом; состояние подготавливаем через API.

Идентификаторы транзакций — новые UUID, STAN и RRN; PAN создаёт API.
Поиск и асинхронные проверки ограничиваются PAN своего теста, затем запись
отбирается GPath по id или STAN. Отсутствие дублей проверяем по данным
конкретной транзакции.
У dashboard и симуляторов нет API для приватного глобального пространства:
для них проверяется форма/арифметика ответа и результат конкретного запуска,
без фиксированного общего числа одобрений или глобальных сумм.

Попарное покрытие поиска — восемь строк для семи необязательных фильтров
при фиксированном приватном PAN. Для каждой пары присутствия фильтров
встречаются 00/01/10/11. Набор содержит цель и семь отвлекающих записей:
каждый включённый фильтр должен убрать свою запись.
Попарное покрытие карт — восемь строк для шести факторов: status, bin,
startDate, endDate, limit 1/2 и offset 0/1, с приватным issuerId.
В нём используются два BIN, три карты и известная таблица допустимых записей.
Проверяем состав и размер страницы. Порядок выдачи карт контрактом не задан.

Идемпотентность Logger проверяется по эффекту и ответу: 201 при новой записи,
200 при повторе, одна запись по PAN и id, 409 при изменении каждого из
19 бизнес-полей. Отдельно проверено, что createdAt и масштаб BigDecimal
не создают ложный конфликт. Повторную авторизацию проверяем отдельно в D-02.

Позитивная асинхронная проверка ожидает запись максимум 15 секунд, опрос —
250 мс. В негативной проверке отсутствие сохраняется 5 секунд при остановленном
брокере и ещё полное окно доставки 15 секунд после его восстановления.
Проверяем баланс и последующую работоспособность публикации.
Проверка отсутствия записи ограничена указанным окном наблюдения.

Тестовый HTTP-прокси подменяет только выбранный путь конкретной карты;
остальные запросы идут реальному CMS/Authorization. С его помощью
воспроизводим ответы зависимости 402/409/503.
После каждого теста правила очищаются. Остановка процессов ограничена
проектом `smp-api-tests`; восстановление выполняется в finally.

За пределами работы: JDBC-проверки, строки и блокировки PostgreSQL,
атомарность конкурентных транзакций, Testcontainers, ack/nack, retry/DLQ/TTL
очередей, WebSocket `/ws/transactions`, UI, нагрузка и проверка точных времён
retry/circuit breaker. Проверки OAuth/401 не входят в набор, поскольку
контроля доступа в СМП нет. Для генератора через API проверяем минимальное
и допустимое количество карт, а также отказ при count=10001. Верхняя граница
10000 покрыта unit-тестами практики 4 без создания 10000 карт в API-прогоне.

Используемые приёмы:

| Приём | Место |
|---|---|
| given/when/then, общая RequestSpecification, фабрики | `ApiSupport`, все тестовые классы |
| MethodSource/ValueSource/CsvSource | `GatewayApiTest`, `LoggerApiTest`, `SearchApiTest` и другие |
| matchesPattern, nullValue, oneOf, hasSize, greaterThanOrEqualTo, notNullValue | Gateway, Authorization, Simulator, Search |
| GPath findAll | Logger redelivery, поиск, сквозная доставка |
| JSON Schema | `shouldApproveValidTransactionAndMatchSchema` |
| Заголовки | `X-Cache`, `Content-Type`, `Retry-After`, `Content-Disposition` |
| Awaitility untilAsserted / during | `awaitTransaction`, `FailureRecoveryApiTest` |
| Источник ожидания и принадлежность ошибки | Комментарии с DTO/контроллером/ТЗ, serviceName и причины отказа |

## 6. Доказательства работоспособности проверок

Для проверки самих тестов намеренно изменяем ожидание или поведение сервиса.
Все три эксперимента завершились падением на проверке результата и **0 errors**.
Скрипт проверяет свежий JUnit XML, ненулевой exit code, наличие failures
и отсутствие errors.

| Тест | Намеренное изменение | Реальный результат |
|---|---|---|
| `shouldApproveValidTransactionAndMatchSchema` | Ожидаемый responseCode 99 вместо 00 | 1 test, 1 failure, 0 errors; фактически 00 |
| Тот же тест схемы | Во временной копии схема требует STAN из пяти цифр | 1 test, 1 failure, 0 errors; ответ содержит шесть цифр |
| `shouldNotDuplicateTransactionOnRedelivery` | Во временной копии `TransactionMapper` сохраняет случайный UUID вместо входного id | 1 test, 1 failure, 0 errors; повтор вернул 201 вместо 200; поиск вернул **total=2 вместо 1** |

В последнем случае через assertAll зафиксированы три нарушения:
потеря исходного id, неправильный HTTP-код повтора и лишняя запись.
Для этого эксперимента использован отдельный образ Logger с изменённым
сохранением ключа дедупликации. После проверки восстановлен исходный образ
и выполнены регрессионные прогоны.

Воспроизводимый скрипт —
[`check-api-tests-mutations.sh`](../../scripts/check-api-tests-mutations.sh).
Полные журналы и XML сохраняются в
`services/api-tests/target/evidence/mutations/`; краткие итоги перенесены
в `verification-results.json`.

## 7. Порядок запуска

Нужны Java 21, Maven, Docker с работающим daemon и Compose v2, Bash и Python 3.
Версии тестовых библиотек закреплены в POM: JUnit Jupiter 5.11.4,
REST-assured и JSON Schema Validator 5.4.0, Awaitility 4.2.2, Hamcrest 2.2.
Jackson управляется зафиксированным Spring Boot parent 3.4.1.
Для Maven настроено публичное зеркало Maven Central в
`services/api-tests/support/maven-settings.xml`. Параметр `-s` позволяет
указать другой файл настроек.

Из корня репозитория:

```bash
# Собрать образы, дождаться health, запустить verify, собрать журналы, удалить тестовый стенд.
./scripts/run-api-tests.sh

# Три последовательных полных прогона.
API_TEST_RUNS=3 ./scripts/run-api-tests.sh

# Явно указать используемое публичное зеркало Maven Central.
./scripts/run-api-tests.sh -s services/api-tests/support/maven-settings.xml
```

Стенд работает в проекте `smp-api-tests` с отдельными сетью и томом данных,
на loopback-портах 18080–18099. Конфигурация содержит тестовые учётные данные
`api_test` для локальной БД и брокера. После прогона скрипт удаляет ресурсы
тестового проекта.

Для исследования расхождений и точечного запуска:

```bash
# Сначала оставить поднятый тестовый стенд.
API_TEST_KEEP_STACK=1 ./scripts/run-api-tests.sh

# Запустить проверки известных расхождений; ожидается 12 падений.
mvn -f services/pom.xml -Papi-tests test -Dgroups=known-defect -Dapi.excludedGroups=

# Отдельный контракт на уже поднятом стенде.
mvn -f services/pom.xml -Papi-tests test -Dtest=LoggerApiTest

# Воспроизвести три намеренные поломки; исходный образ восстанавливается автоматически.
./scripts/check-api-tests-mutations.sh

# Явно убрать оставленный диагностический стенд.
docker compose --env-file /dev/null -p smp-api-tests -f docker-compose.api-tests.yaml down --volumes
```

Дополнительные Maven-параметры передаются скриптам без преобразования,
включая `-s services/api-tests/support/maven-settings.xml` и `-Dtest=...`.
`API_TEST_SKIP_BUILD=1` переиспользует ранее собранные образы.
Для самостоятельного запуска `FailureRecoveryApiTest` нужны
`-Dapi.manageStack=true -Dapi.projectRoot=/абсолютный/путь/к/репозиторию`;
общий скрипт задаёт их автоматически.

В CI настроен автоматический запуск на push/PR с изменениями services,
скриптов, Compose или workflow: три регрессионных прогона, отдельный запуск
`known-defect`, публикация JUnit XML и Compose-журналов. Для шага `known-defect`
задан `continue-on-error`, результат отображается в summary. Удаление стенда
и сбор артефактов выполняются с `if: always()`.

Локальное окружение: macOS ARM64, Java 21.0.11, Maven 3.10.0, Docker/Colima.
Три регрессионных прогона завершились успешно; Checkstyle и pre-commit пройдены.
