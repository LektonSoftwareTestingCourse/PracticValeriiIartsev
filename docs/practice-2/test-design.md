# Тест-дизайн: Authorization и Card Management

Источники требований: [AUTH](../../tz/04-authorization.md) (§2 — авторизация, §3 — резервирование средств, §4 — лимиты, §5 — отказ CMS), [CMS](../../tz/05-card-management.md) (§2 — CRUD, §3 — генерация тестовых карт, §4 — Проверка и генерация контрольной цифры PAN (алгоритм Луна), §5 — резервирование средств) и [API-контракт](../api/openapi.yaml) (`AuthorizationRequest.amount ≥ 1`). Суммы и лимиты — в копейках. `expiryDate` — MMYY; тестовые часы фиксируются на 24.09.2026. Для отрицательных кейсов меняется один входной класс, если явно не проверяется приоритет отказов.

| Поле и требование | Класс | Представитель | Ожидание |
|---|---|---|---|
| Статус, AUTH §2 | ACTIVE | ACTIVE | APPROVED |
| Статус, AUTH §2 | NOT ACTIVE | INACTIVE | DECLINED |
| PAN, AUTH §2 | известный| сохранённый| Продолжить|
| PAN, AUTH §2 | отсутствующий | другой 16-значный | DECLINED, 14 |
| Срок, AUTH §2 | текущий или будущий месяц | 0926 | APPROVED |
| Срок, AUTH §2 | прошедший месяц | 0826 | DECLINED, 54 |
| Сумма + usage, AUTH §2, §4 | в пределах | 100/100 | APPROVED |
| Сумма + usage, AUTH §2, §4 | выше дневного остатка / выше месячного остатка | 101/100 по дневному | DECLINED, 61 |
| Сумма и баланс, AUTH §2 | хватает | 100/100 | APPROVED |
| Сумма и баланс, AUTH §2 | не хватает | 101/100 | DECLINED, 51 |
| BIN при создании, CMS §2 | 6 цифр | 400000 | Создать карту |
| BIN при создании, CMS §2 | неверная длина / недесятичный | 40000 | не создавать карту |
| `expiryDate`, CMS §2 | результат создания | MMYY через 3 года | Сохранённое 4-значное значение |
| Резерв, CMS §5 | меньше баланса, равен балансу | 99/100, 100/100 | Остаток 1, остаток 0 |
| Резерв, CMS §5 | больше баланса | 101/100 | остаток без изменения |

## Граничные значения

Берем граничные точки баланса/лимитов. Для AUTH остальные ограничения не мешают. При проверке дневного лимита месячный остаток и баланс = 1000, при проверке месячного — дневной остаток и баланс = 1000, при проверке баланса — оба остатка = 1000. Сумма транзакции 100; меняется остаток соответствующего ограничения.

| Требование | Граница | OFF− / ON / OFF+ | Результат |
|---|---|---|---|
| AUTH §2, §4 | `dailyLimit − dailyUsage = amount` | остаток 99 / 100 / 101 | 61 / 00 / 00 |
| AUTH §2, §4 | `monthlyLimit − monthlyUsage = amount` | остаток 99 / 100 / 101 | 61 / 00 / 00 |
| AUTH §2 | `availableBalance = amount` | баланс 99 / 100 / 101 | 51 / 00 / 00 |
| AUTH §2 | последний допустимый месяц `expiryDate` | 0826 / 0926 / 1026 | 54 / 00 / 00 |
| API-контракт | минимальная сумма 1 копейка | 0 / 1 / 2 | отказ / 00 / 00 |
| CMS §2 | допустимый месяц `expiryDate` | 31.12.2026/-/01.01.2027| при создании допустимы только месяцы 01…12 |

Ожидания APPROVED для отдельных классов предполагают, что остальные проверки пройдены. Класс NOT ACTIVE проверяется всеми тремя статусами: причины отказа различаются. Превышение дневного и месячного лимитов проверяется раздельно.

## Общие предусловия и проверки

Каждый кейс независим: отдельная карта, исходные баланс и usage. Дата — 24.09.2026, время запроса и тестовые часы согласованы. Исключения даты указаны в кейсах. Статус, срок и историю расходов задаём фикстурой БД или заглушкой CMS.

**База AUTH:** карта ACTIVE, срок `1026`, баланс 1000; дневной usage 200, месячный 500 (200 сегодня + 300 ранее в сентябре). Дневной лимит 1200, месячный 1500: оба остатка 1000. Запрос — сумма 100, POS, MCC 5411, существующий PAN; остальные обязательные поля соответствуют `AuthorizationRequest`.

Остаток лимита R задаётся как `limit = usage + R`. Во всех успешных AUTH-кейсах дополнительно проверяются RRN из 12 цифр, authCode из 6 символов A–Z/0–9 и увеличение обоих usage на сумму. При отказе резерв отсутствует, баланс и usage неизменны. Состояние проверяется через CMS и БД; при недоступном CMS — напрямую в БД.

**База CMS:** зарегистрированы BIN 400000 и 400001; тело создания — BIN 400000, `cardholderName=IVAN IVANOV`, валюта 643, лимиты 1200/1500, initialBalance 1000. Для reserve — отдельная карта и новый 12-значный RRN.

## Попарное тестирование Authorization

[Модель](pict/model.txt) содержит 7 бизнес-факторов. При сумме 100 значения `below/equal/above` означают остатки 101/100/99; `future/current_month/past` — сроки 1026/0926/0826 при дате 24.09.2026.

Для обычного отказа по статусу фиксируются будущий срок, все сравнения below, POS и MCC 5411. Для обычного отказа по сроку — все сравнения below. Это осознанное сокращение покрытия.

В [seeds.txt](pict/seeds.txt) закреплены два кейса:

- BLOCKED, past, все above, POS, MCC 5411 → CARD_BLOCKED.
- ACTIVE, past, все above, POS, MCC 5411 → responseCode=54.

Ограничения явно разрешают эти два исключения. Seeds обеспечивают их включение в набор и не обходят ограничения. Набор допустимых бизнес-комбинаций сохранён; технический фактор `scenario` удалён.

```sh
pict docs/practice-2/pict/model.txt /e:docs/practice-2/pict/seeds.txt > docs/practice-2/pict/cases.txt
```

## Попарное тестирование Card Management

Область — `POST /api/cards` (CMS §2, §4; API: `CardCreateRequest`). Генерация пакетов, чтение, PATCH, удаление и reserve остаются в C-кейсах.

[Модель](pict/card-management/model.txt) содержит 7 факторов:

| Фактор | Значения → данные запроса |
|---|---|
| bin_class | known_400000 / known_400001 → 400000 / 400001; short → 40000; non_numeric → 40000A |
| holder_name | normal → IVAN IVANOV; max_length → 255 букв A; missing → поле отсутствует; too_long → 256 букв A |
| currency | RUB → 643; USD → 840; invalid → 64A |
| daily_limit | default → поле отсутствует (15000000); custom → 1200 |
| monthly_limit | default → поле отсутствует (300000000); custom → 1500 |
| initial_balance | default → поле отсутствует (100000000); zero → 0; positive → 1000 |
| creation_date | september → 24.09.2026; year_end → 31.12.2026; year_start → 01.01.2027 |

**Ограничение:** не более одного невалидного поля среди BIN, имени и валюты. Это исключает маскировку причин отказа; сочетания нескольких ошибок намеренно не покрываются. Лимиты и баланс не связываются между собой: такого ограничения для создания карты в ТЗ нет.

[Seeds](pict/card-management/seeds.txt) закрепляют три успешных запроса: значения по умолчанию, нулевой и положительный баланс. Эти строки удовлетворяют ограничениям; PICT включает их в набор и дополняет недостающие пары.

```sh
pict docs/practice-2/pict/card-management/model.txt /e:docs/practice-2/pict/card-management/seeds.txt > docs/practice-2/pict/card-management/cases.txt
```

В [наборе](pict/card-management/cases.txt) 19 кейсов: 3 позитивных и 16 негативных; покрыты 179 разрешённых пар. Первая строка — заголовок.

Общие предусловия CP: CMS и БД доступны, оба BIN зарегистрированы. Каждый кейс независим; часы задаются по creation_date, число карт фиксируется перед запросом. Неуказанных полей в JSON нет; `default` означает отсутствие поля, а не null.

Для успеха дополнительно проверить: одна новая карта, status=ACTIVE, PAN из 16 цифр с заданным BIN и верной цифрой Луна, имя и валюта соответствуют запросу. Ответ и последующий GET должны совпадать по сохранённым полям. Для отказа: HTTP 400 и отсутствие новой карты.
