# Тест-кейсы и анализ пирамиды

## Правила выбора уровня

| Уровень | Что реально проверяем | Что поднимаем |
|---|---|---|
| unit | Ветвление, вычисление, вызовы зависимостей публичного метода | Один класс/небольшая группа классов; моки внешних зависимостей, без сети и БД |
| api | HTTP-маршрут, валидацию, сериализацию и коды ответа | Настоящий HTTP-слой проверяемого сервиса; стаб следующего сервиса/бизнес-логики |
| integration | SQL, транзакции, блокировки, реальное взаимодействие HTTP/AMQP с зависимостью | Участвующие компоненты, PostgreSQL и/или RabbitMQ; контролируемые fault injection |
| e2e | Пользовательский результат через полный процессинг | Реальный контур Gateway → Switch → Authorization → CMS, Logger, БД и очередь; UI для N-19 |

**Unit-first:** бизнес-правила, границы значений и попарные комбинации проверяем через публичные методы сервисов, доменные модели и DTO-валидаторы. HTTP, БД и очередь не нужны для каждой комбинации входных данных.

Кейсы практики 2 ниже **адаптированы для автоматизации**, а не просто переименованы: сохраняются ID и входные данные, но для unit меняются шаги и оракул. Вместо POST/GET и чтения таблиц — вызов метода, проверка результата/исключения и аргументов зависимостей. `verify(repository).save(...)` доказывает передачу объекта, **не** commit в БД. Реальные SQL-условия, ограничения хранения, транзакции и доставку оставляем отдельным интеграционным проверкам; HTTP-коды — API-проверкам.

### Как устроены unit-проверки

| Объект | Тестовая граница | Оракул |
|---|---|---|
| `AuthServiceImpl.authorize()` | Настоящий сервис; Mockito-моки CMS/BIN-клиентов, LimitUsageRepository и notifier | status/code/reason, формат RRN/authCode, точные аргументы reserve/upsert и отсутствие ненужных вызовов |
| `RouteService.route()`, `RoutingService.getIssuerIdByPan()` | Настоящий проверяемый класс; клиенты и публикация — моки, BIN-map — фикстура | Выбор issuer, отказ, содержимое сообщения и команда компенсации; без HTTP/AMQP |
| `CardServiceImpl` | Настоящий сервис и модели; репозитории, генератор PAN, notifier — моки; TransactionRunner исполняет переданный callback | Поля возвращаемого объекта, ArgumentCaptor для create/update/save, исключения; без доказательства транзакционности |
| `Card`, `Reservation`, `LuhnValidator`, `CardExpiryDateMapper` | Настоящие объекты без Spring-контекста | Расчёт баланса/срока, переходы состояний, формат PAN, независимая контрольная сумма |
| `CreateCardRequest`, `AuthorizationRequest` | Bean Validation без запуска приложения | Набор нарушенных полей; HTTP-ответ и обращение к БД не проверяются |
| `TransactionRequestValidator`, `TransactionValidationFilter` | Прямой вызов; для фильтра — MockServerWebExchange, мок GatewayFilterChain и StepVerifier | Ошибка валидации, ответ в mock exchange, отсутствие/наличие вызова цепочки; это не проверка реального маршрута Gateway |

Наборы A/P и CP удобно параметризовать через JUnit `@ParameterizedTest`. Проверяем публичное поведение, не приватные методы. Приведённый план не означает, что все перечисленные автотесты уже реализованы.

## Общие данные и правила выполнения

- Отдельные PAN, STAN, RRN/transactionId на независимые кейсы; никакой зависимости от порядка выполнения. Только синтетические карты учебного стенда.
- База AUTH из практики 2: ACTIVE, срок `1026`, баланс 1000; daily usage 200, monthly usage 500; лимиты 1200/1500; сумма 100 копеек. UTC-время запроса `2026-09-24T10:00:00Z`. BIN `400000` → `ISS001`.
- Остальные поля авторизации валидны: `mti=0100`, STAN — 6 цифр, PAN — 16 цифр, processingCode — 6 символов, currencyCode `643`, terminalId — 8 символов, merchantId — 15 символов, terminalType `POS`, mcc `5411`, acquirerId `ACQ001`, issuerId `ISS001` для прямого запроса в Authorization. Внешний запрос может не задавать issuerId: его определяет Switch.
- База CMS: BIN `400000` зарегистрирован, имя `IVAN IVANOV`, валюта `643`, все суммы заданы явно; в новых кейсах не полагаемся на спорные defaults.
- В E2E Merchant Acquirer доступен как настоящий поставщик комиссии для Switch, но генераторы нагрузки не запускаются; Terminal Simulator заменён тестовым HTTP-клиентом. Комиссия не входит в оракул N-19/20.
- API-кейсы выполняются без посторонних отказов rate limiter/circuit breaker; их состояние изолировано или сброшено. Моки не заменяют тот компонент, чьё поведение проверяется.
- Асинхронные проверки: опрос нужной строки каждые 100 мс, deadline 10 с после разрешения обработки. Это **бюджет теста**, не SLA. При превышении — ошибка с состоянием очереди/outbox и идентификаторами, не бесконечный retry и не слепой `sleep`.
- Искусственные отказы и паузы снимаются в `finally`; очереди/таблицы очищаются только в выделенном тестовом окружении. Остановка рабочего пользовательского стенда не требуется.
- В unit дата авторизации задаётся через `transmissionDateTime`; для C-10/C-15 и успешных CP фиксируем `YearMonth.now()` локальным `mockStatic` в `try-with-resources`. Реальные `YearMonth` для фикстур создаём до открытия static mock; вызов и проверка выполняются в том же потоке. Внедряемого `Clock` у `Card.fromDraft()` сейчас нет. Системные часы стенда менять не нужно.
- Репозиторий в unit возвращает явно заданные 0/1, Optional или объект; не имитируем в Mockito весь SQL. Для DTO остальные поля валидны, чтобы нарушение проверяемого поля не скрывалось посторонней ошибкой. Для успешного сценария `merchantId` должен содержать ровно 15 символов.
- Проверки БД, HTTP-fault и асинхронные ожидания из общих условий применяются только к соответствующим integration/API/E2E-кейсам, не к unit.

### Почему новые кейсы не подняты выше необходимого

- N-01–06 обходятся публичными методами и моками/стабами.
- N-07–10 проверяют HTTP-границу, но не сохранение денег: вместо полного стенда достаточно реального web-слоя и стабов.
- N-11–18 оставлены integration именно ради SQL, транзакций и протокола AMQP, а не ради перебора бизнес-условий. N-11 проверяет арифметику, которую моки A-09–14/P не исполняют. N-05 и N-15 не дублируют один оракул: первый проверяет команду компенсации, второй — её эффект в БД.
- Только N-19–20 проверяют совместимость полного маршрута. В N-19 UI существенен; в N-20 достаточно полного backend-пути, UI не нужен для доказательства отказа.

### Уточнения старых ожиданий по коду

Исходный `practice-2/test-design.md` не переписан. Ниже — вопросы к ожиданиям, которые сохраняются и после unit-адаптации. Возможный дефект реализации не превращается автоматически в новое «правильное требование»; unit-тест с таким ожиданием может выявлять известное расхождение, а не быть зелёной регрессией.

|---|---|---|
| A-18 | 05 / ISSUER_TIMEOUT при недоступном GET CMS | [AuthServiceImpl][auth] возвращает [SERVICE_UNAVAILABLE][declines]. Unit воспроизводит ServiceUnavailableException из клиента и сравнивает reason; реальный fault-proxy для этой проверки не нужен. HTTP 503 контроллера — отдельный контракт. |
| A-19 | Сумма 0 отклонена прямым Authorization | [AuthorizationRequest.amount][authrequest] помечен `@PositiveOrZero`, поэтому Validator не отклоняет 0. [Gateway validator][validator] требует `>0`, но его unit/API-проверки не закрывают этот разрыв прямого входа. A-19 остаётся требованием с расхождением; не выдавать его за уже подтверждённое поведение. |
| P-14, P-20 | Код 61 при нехватке лимита и баланса | [authorize()][auth] проверяет баланс до SQL-лимитов, поэтому при этих данных возвращает 51. N-04 отдельно фиксирует нынешний порядок. P-01/P-02 не затронуты: статус и срок остаются раньше баланса. |

## Часть Г — анализ пропорций

### Подсчёт

Каждый ID учитывается один раз по основному уровню. Параметры JUnit и несколько проверок одного сценария не увеличивают число ID. Это **96 спроектированных логических кейсов**, не количество реализованных/прошедших автотестов, не покрытие кода и не длительность CI. Известные расхождения A-18/A-19, P-14/P-20, CP-01/07/09/15, N-14/N-18 входят в план, но не объявляются реализованным поведением.

| Уровень | Адаптированные (пр. 2) | Новые (часть Б) | Итого | Доля |
|---|---:|---:|---:|---:|
| unit | 74 | 6 | 80 | 83,33% |
| api | 0 | 4 | 4 | 4,17% |
| integration | 2 | 8 | 10 | 10,42% |
| e2e | 0 | 2 | 2 | 2,08% |
| **Итого** | **76** | **20** | **96** | **100,00%** |

Формула: `доля = число кейсов уровня / 96 × 100%`, округление до двух знаков. Проверка: `21 A + 14 C + 22 P + 19 CP = 76`; unit — все A/P/CP и 12 C, integration — C-06/C-12. Новые: N-01–06 unit, N-07–10 api, N-11–18 integration, N-19–20 e2e. Средний слой api + integration: 14 кейсов, 14,58% (сумма отдельно округлённых долей может отличаться на 0,01%).

### Почему такое распределение

1. **Широкое unit-основание.** Статус, срок, баланс, приоритеты отказов, валидация, генерация и изменение моделей проверяются без сети. Вместо повторения полного контура для каждой строки PICT используются параметризованные unit-тесты.
2. **Интеграции проверяют то, чего не доказывают моки.** N-11 — реальные дневные/месячные SQL-границы; N-12/N-15 — сохранение резерва и компенсации; N-16 — rollback карты вместе с outbox; N-13/N-17/N-18 — сериализация, доставка и очереди. C-06/C-12 сохраняют SQL-оракулы скрытия и выборки карт.
3. **API проверяется отдельно от бизнес-логики.** N-07–10 нужны для маршрута, валидации на HTTP-границе и кодов ответа. Ни прямой вызов Validator, ни фильтр с MockServerWebExchange не доказывают работоспособность маршрута приложения.
4. **E2E ограничены двумя результатами.** Покупка с журналом/Dashboard и отказ после блокировки карты. Перебор граничных значений и отказов зависимостей не переносится на этот дорогой уровень.
5. **70/20/10 — ориентир, не квота.** Доля unit выше из-за попарных наборов и границ. Это не доказательство полного покрытия: SQL-блокировки и конкуренция, уникальность batch-сохранения, полный набор HTTP-кодов и поведение инфраструктуры требуют своих проверок, а не формального роста процента unit.

### Порядок автоматизации

- Начать с параметризованных unit A/P и CP, моделей Card/Reservation, сервисов карты/маршрутизации и валидации Gateway. Проверять публичные методы, возвращаемые объекты и команды зависимостям; не мокать сам проверяемый класс.
- Для A-09–14/P не выдавать заранее заданный ответ upsert за проверку SQL. Границы сумм проверить отдельно в N-11; для C-06/C-12 сохранить реальную БД.
- Не дублировать все unit-комбинации через HTTP: добавить ограниченный набор контрактов N-07–10. Ожидания HTTP 400/402/404 из старых сценариев не считать подтверждёнными соответствующими unit-тестами.
- После быстрых unit/API проверять интеграционные инварианты N-11–18, затем два E2E. Не запускать пользовательский стенд для теста чистого условия.
- N-14/N-18 сохранять как проверки требований с известными пробелами реализации. Наличие RabbitMQ-настройки не доказывает ожидание confirm или три попытки consumer; таймеры и фактическую доставку нельзя подтвердить Mockito.
- Отчёт автоматизации вести отдельно: какие кейсы реализованы, какие прошли, какие выявляют расхождение. Этот документ задаёт план и границы, а не результаты прогона.
